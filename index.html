Air Quality Case Study

An educational, self-contained walkthrough of 9,357 hourly air quality readings from a heavily polluted Italian city (March 2004 – April 2005) — seasonal trends, WHO threshold exceedances, hourly patterns, and temperature effects. Every panel below is annotated with what the underlying SQL query does and why — this dashboard doubles as a teaching artifact for the pipeline that built it.

Step 1 — A data-quality catch: two Benzene stats in the original coursework were wrong. Independently recomputing every column's -200 (missing-value) count against the raw CSV found that Benzene's documented "1,639 missing (17.5%)" figure is actually the missing-value count for NOx(GT), a different column — Benzene's real count is 366 (3.9%). Its documented value range ("0 to 9.9 microg/m^3") was also stale — the true range is 0.1 to 63.7. Both are corrected here and in AirQuality.sql; if anything, the lower missing-rate makes the WHO exceedance finding in Tab 3 more trustworthy, not less, since it rests on a far more complete column than originally believed.

Step 3 — Which pollutants actually cross WHO guideline levels? SQL Query 3 counts both exceedance-hours and distinct exceedance-days against three WHO Air Quality Guideline thresholds: CO > 10 mg/m^3 (8-hour mean), NO2 > 200 microg/m^3 (1-hour mean), and Benzene > 5 microg/m^3 (annual guideline, used here as an hourly proxy). Benzene's near-total exceedance rate reflects the guideline being an annual average threshold applied to individual hourly readings — a deliberately strict test, but still a meaningful signal given chronic Benzene exposure's links to leukemia and other blood disorders.

Step 4 — Rush-hour patterns and the temperature hypothesis. SQL Query 4 groups by hour-of-day to test whether pollution tracks traffic patterns. SQL Query 5 buckets temperature into four ranges to test whether colder air (reduced atmospheric mixing) correlates with higher pollutant concentrations — the monthly view in Tab 2 supports this seasonally, though the hour-level temperature-bucket view below is noisier and worth reading critically rather than assuming a clean monotonic relationship.

Step 5 — The pipeline behind this dashboard, end to end:
  1. pandas.read_csv() loads the raw UCI CSV, handling two dataset-specific quirks: semicolon delimiters and European decimal-comma formatting (e.g. "2,6" instead of "2.6"), plus 2 trailing empty columns and ~114 fully-blank trailing rows dropped to reach the documented 9,357-row count.
  2. df.to_sql() loads the cleaned table into a local SQLite database — no server required.
  3. A SQL view (airquality_clean) replaces -200 placeholders with NULL via NULLIF() and reformats the date column — the same cleaning logic as the original MySQL view, translated to SQLite syntax (STR_TO_DATE → string slicing, since SQLite has no native equivalent).
  4. Five SQL queries — the same structure as the original MySQL analysis (AirQuality.sql) — answer each research question: monthly averages, peak/low months per pollutant, WHO threshold exceedances, hourly patterns, and temperature buckets.
  5. Independently recomputing every number against the raw CSV is what surfaced the two Benzene documentation errors described in Tab 1 — a concrete example of why re-deriving results from source data (rather than trusting prior write-ups) is worth doing.
  6. Each result is pulled back into pandas, exported to CSV, and bundled into dashboard_data.json — the exact numbers rendered in this dashboard.
  7. This HTML file embeds that JSON directly and renders it with Chart.js, so the dashboard opens and works completely offline — no server, no live database connection.

Full source: analysis/run_analysis.py (heavily commented) and AirQuality.sql (the original MySQL version, with corrections noted inline) in this repository.
